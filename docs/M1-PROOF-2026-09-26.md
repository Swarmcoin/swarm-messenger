## 5. The blockers, exactly

### 5.1 No Visual Studio, and it cannot be installed

`node-gyp` will not even _configure_ without it. Four failures, three of which
were for work that does not need to happen on Windows:

- `packages/mute-state-change` is a macOS-only addon. Its `binding.gyp` declares
  an empty `noop` target elsewhere, but node-gyp still ran configure and demanded
  MSVC. Now skipped on non-macOS by its own `install` script.
- `packages/windows-ucv` (Windows Hello re-authentication) genuinely needs MSVC.
  Skipped only when `SWARM_ALLOW_MISSING_NATIVE=1`; CI never sets it. The module
  no longer throws at import when the addon is absent, and `promptOSAuth()`
  reports `unsupported`, which is what a PC with no Windows Hello device reports.
- `electron-builder install-app-deps` (`@electron/rebuild`) invokes node-gyp
  directly, bypassing those scripts, so it has the same wrapper.

**Every native dependency that actually ships uses a prebuilt binary** and needed
no compiler: `@signalapp/libsignal-client` 0.101.2,
`@signalapp/sqlcipher` 4.1.0 (node-gyp-build), `@signalapp/ringrtc` 2.72.0
(downloads a prebuild), `@indutny/simple-windows-notifications`.

Consequence: a local build is fine for development. **A release build must come
from CI**, where `windows-latest` has MSVC and nothing is skipped.

### 5.2 libsignal-net cannot be pointed at a SWARM hostname — the important one

`libsignal-client` 0.101.2 exposes exactly three network environments
(`dist/net.d.ts`, `NetConstructorOptions`): Signal staging, Signal production —
both with Signal's hostnames compiled into the Rust crate — and `localTestServer`,
which only accepts a loopback host and port plus a supplied root certificate.

Upstream `resolveLibsignalNet()` **fell through to `Environment.Production` for
any hostname it did not recognise**. With `serverUrl = https://chat.swarm.green`
that means the chat and registration traffic would have gone to **Signal's
production servers** — the one thing this project must never do.

It now refuses, with a message saying what has to change, and the app still starts
and shows its window (the refusal surfaces when something actually touches the
network). The server fork's own `docs/STAGING.md` reaches the same conclusion
independently.

Until Opus M-D's `swarm-libsignal` fork adds a SWARM environment, the only working
route is loopback: the staging chat server reachable at `https://localhost:<port>`,
directly or through a tunnel, with its root certificate in `certificateAuthority`.
`docs/SWARM-CONFIG.md` names the exact three places to change when the fork lands,
and a test asserts today's answer so step 2 cannot be forgotten.

### 5.3 The server parameters do not exist yet

`serverPublicParams`, `genericServerPublicParams`, `backupServerPublicParams` and
`serverTrustRoots` are generated by the chat server. They are
`SWARM-PLACEHOLDER-*` strings, and the app **refuses to start** while any of them
is present — `app/swarmStartupGuard.main.ts`, before any window opens, with a
plain-language dialog naming each one.

`SWARM_ALLOW_PLACEHOLDER_CONFIG=1` continues past it on an **unpackaged** tree
only; a packaged build ignores the variable, so no installer can bypass the check.
An endpoint on a Signal host is refused with **no** override at all.

One command wires the real values in when they exist:
`node scripts/swarm-import-params.mjs`.

## 6. What a reviewer should check first

1. `git diff upstream-abe80d3..swarm-main -- config/` — no Signal endpoint, no
   Signal zk parameter, no Signal trust root, no Stripe key, no update feed.
2. `pnpm run test-node` — the SWARM endpoint scan is in there.
3. The About window — the AGPL attribution must read exactly "SWARM Messenger is
   based on Signal Desktop by Signal Messenger, LLC, AGPL-3.0".
4. `node scripts/swarm-brand-check.mjs release` after a build — it fails on a
   Signal domain anywhere in the packaged app, or on any packaged English string
   that says "Signal" other than the attribution.
